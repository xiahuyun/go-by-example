# tx-verify（验证 bbolt 并发读写是否互相阻塞）

这个小项目会跑两组实验：

1. 长时间只读事务进行中，再发起写事务，观察写事务等待时间。
2. 长时间写事务进行中，再发起读事务，观察读事务等待时间。

## 运行

在 `etcd/bbolt` 目录执行：

```bash
go run ./tx-verify
```

## 如何看结果

每组实验会输出两项关键指标：

- `等待进入事务耗时`：从调用 `View/Update` 到真正进入事务回调的等待时间。
- `事务回调执行耗时`：进入回调后，执行读写逻辑本身花费的时间。
- `回调结束后等待耗时`（仅写事务场景）：通常对应 `Commit` 阶段等待（例如等待活跃读事务释放）。
- `整个调用总耗时`：本次调用从开始到结束的总时间。

默认写入包含一个 `32MiB` 的 value，用于更容易触发提交阶段的真实等待。

通常可以观察到：

- 读期间发起写：写事务可以快速进入回调，但提交阶段可能等待读事务结束。
- 写期间发起读：读事务通常可以快速进入并读取旧快照，不明显等待写事务结束。

## 源码分析：为什么“写会被读影响”

下面结论基于 `go.etcd.io/bbolt v1.4.3` 源码：

1. 读事务会在整个生命周期持有 `mmap` 的读锁  
   - `beginTx()` 中加 `db.mmaplock.RLock()`（`db.go`）  
   - 直到读事务关闭，`removeTx()` 才 `RUnlock()`（`db.go`）  
   - 这意味着活跃读事务会长期占用 `mmaplock` 的读锁。

2. 写事务开始时不会先抢 `mmap` 写锁  
   - `beginRWTx()` 只先拿 `db.rwlock`（单写者互斥），并不拿 `mmaplock`（`db.go`）  
   - 所以你会看到“写事务很快进入回调”。

3. 写事务在 `Commit` 期间可能需要重映射（`mmap`），这里会被读事务卡住  
   - `Update()` 在用户回调后执行 `t.Commit()`（`db.go`）  
   - `Commit()` -> `root.spill()` -> `node.spill()` -> `tx.allocate()` -> `db.allocate()`  
   - 当空间不够时，`db.allocate()` 会调用 `db.mmap(minsz)`（`db.go`）  
   - `db.mmap()` 需要 `db.mmaplock.Lock()`（写锁，`db.go`）  
   - 该写锁必须等待所有读锁释放，所以长读事务会让写提交阶段等待。

4. 长读事务还会延迟旧页回收，间接提高写事务触发扩容/重映射的概率  
   - 读事务开始/结束会登记 `AddReadonlyTXID` / `RemoveReadonlyTXID`  
   - 写事务开始时 `ReleasePendingPages()` 只能释放“早于最老活跃读事务”的 pending pages  
   - 因此长读事务会让可复用页减少，更容易走到 grow/mmap 路径。

## 对本实验现象的解释

- `等待进入事务耗时` 很小：因为写事务开始时主要竞争的是 `rwlock`，不是 `mmaplock`。
- `回调结束后等待耗时` 很大：主要耗在 `Commit` 里的分裂/分配/扩容/重映射阶段，等待读事务释放 `mmaplock.RLock`。
- `写期间读几乎不等`：读事务可基于当前映射快速拿到只读快照；只有在极短的重映射窗口才可能被 `mmaplock.Lock` 暂时阻塞。
